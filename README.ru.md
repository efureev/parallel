[![Test](https://github.com/efureev/parallel/actions/workflows/test.yml/badge.svg)](https://github.com/efureev/parallel/actions/workflows/test.yml)

*Read this in [English](README.md).*

Небольшая CLI-утилита для параллельного запуска нескольких консольных команд с читаемым цветным
выводом. Полезна при локальной разработке, когда нужно поднять сразу несколько сервисов и
инструментов: веб-сервер, очереди, сборщики, вотчеры.

Коротко о главном:

- Параллельное выполнение независимых цепочек
- Внутри цепочки: обычные команды идут последовательно, команды с `pipe: true` — одновременно
- Читаемые цветные логи с раскраской по цепочкам и потоковой отдачей (`pipe`)
- Мягкое завершение: исходный сигнал ОС уходит всей группе процессов, утилита дожидается их
- Конфигурация в YAML, helpers для Docker, шаблоны имён

В этом файле собраны типичные сценарии и практические примеры.

## Установка

Требования: Go 1.26+ (проверено на macOS, Linux, Windows)

```shell
go install github.com/efureev/parallel@latest
```

Бинарник окажется в `$(go env GOPATH)/bin/parallel`.

## Быстрый старт

Если файл `.parallelrc.yaml` (или `.parallelrc.yml`) лежит в рабочем каталоге — либо в любом
каталоге выше:

```shell
parallel
```

Поиск поднимается по дереву каталогов, как это делает `git` со своей конфигурацией, поэтому
файл, закоммиченный в корне проекта, работает из любого подкаталога. Побеждает ближайший
каталог, а внутри одного каталога `.yaml` предпочитается `.yml`. Относительные значения `dir`
разрешаются от найденного файла, так что конфигурация целиком не зависит от места запуска.

Если конфигурация лежит в другом месте:

```shell
parallel -f /path/to/config/flow.yaml
```

В репозитории есть два готовых примера, их не нужно править перед запуском:

```shell
parallel -f examples/basic.yaml   # две цепочки: последовательная и потоковая
parallel -f examples/full.yaml    # env, dir, disable и режим Docker
```

Поддерживаемые флаги:

- `-f` — путь к YAML-конфигурации; если не задан, `.parallelrc.yaml` / `.parallelrc.yml`
  ищется в текущем каталоге и во всех родительских
- `-except <имена>` — цепочки, которые надо пропустить, через запятую
- `-list` — показать, какие цепочки определены, и выйти
- `-dry-run` — показать, что именно запустится, и выйти, ничего не запуская
- `-keep-going` — не останавливать соседние цепочки при отказе одной из них
- `-timeout <длительность>` — снимать команду, если она работает дольше (например, `30s`, `5m`)
- `-jobs <n>` — запускать не больше `n` цепочек одновременно (перекрывает `maxParallel`)
- `-no-color` — отключить раскраску
- `-log-level` — `debug`, `info` (по умолчанию), `warn` или `error`
- `-v`, `--version` — информация о версии
- `-h`, `--help` — справка

Позиционные аргументы отбирают цепочки, а `--` переключает в режим запуска команд вовсе без
конфигурации:

```shell
parallel api ui                              # запустить только эти цепочки
parallel -except worker                      # всё, кроме этой
parallel -list                               # что вообще определено в конфигурации?
parallel -dry-run api                        # что именно запустит `parallel api`?
parallel -keep-going                          # показать все отказы, а не только первый
parallel -timeout 5m                          # ни одна команда не работает дольше пяти минут
parallel -- 'go run ./cmd/api' 'yarn dev'    # без файла конфигурации вообще
```

Раскраска подчиняется соглашению [NO_COLOR](https://no-color.org): переменная `NO_COLOR`
отключает её, `FORCE_COLOR` включает при выводе не в терминал, а флаг `-no-color` сильнее обеих.

Неизвестные поля в конфигурации отвергаются с указанием точной позиции и подсказкой: опечатка
вроде `pipeline:` вместо `pipe:` падает громко, а не меняет поведение молча.

### Коды возврата

Утилита пригодна для скриптов и CI и возвращает осмысленный код:

- `0` — все цепочки отработали успешно (а также для `-v` и `-h`).
- `1` — ошибка запуска или конфигурации: файл не найден, неизвестное поле, неверный флаг.
- `124` — команда снята за превышение `timeout`. Значение выбрано по соглашению `timeout(1)`:
  у снятого процесса собственного статуса нет, и выбирать всё равно приходится.
- *собственный код команды* — если команда упала, её статус пробрасывается наружу, поэтому
  `parallel -f flow.yaml || echo $?` показывает, что произошло на самом деле. Если упало
  несколько команд, побеждает первая в порядке объявления в конфигурации.

Это позволяет безопасно использовать `parallel` в скриптах и пайплайнах
(например, `parallel -f flow.yaml && next-step`).

### Когда падает одна из цепочек

По умолчанию отказ цепочки останавливает остальные: если в наборе для разработки упал API,
держать фронтенд обычно незачем. В CI чаще нужно обратное — запустив линтер, тесты и сборку
тремя цепочками, хочется увидеть все отказы разом, а не первый и потом ещё два прогона. Для
этого есть `-keep-going`, он же `failFast: false` в конфигурации:

```yaml
failFast: false     # ключ верхнего уровня, рядом с `commands`
commands:
  lint: ...
  test: ...
```

Явный флаг сильнее файла, поэтому `-keep-going=false` возвращает поведение по умолчанию для
одного запуска.

`-keep-going` действует только на цепочки относительно друг друга. Внутри цепочки ничего не
меняется: упавшая не-`pipe` команда по-прежнему отменяет остаток **своей** цепочки, потому что
команды в ней обычно зависимы — запускать `serve` после провалившейся `migrate` значило бы
работать с заведомо сломанным состоянием.

> Следствие, о котором стоит знать: с `-keep-going` упавшая цепочка больше не обрывает
> долгоживущего соседа. Поэтому запуск, в котором есть dev-сервер, сам не завершится — раньше
> его снимала отмена.

### Итоговая сводка

Если цепочек больше одной, в конце печатается сводка. Запуск закончился, вывод пяти цепочек
перемешан, и она отвечает на вопрос «так что же сломалось» без листания вверх:

```
Summary:
  api     ok       1.2s
  worker  failed   0.3s  command execution failed: command "bad" in chain "worker" exited with status 42
  ui      stopped  0.3s
```

Перезапускаемая команда ещё не считается упавшей, поэтому при поведении по умолчанию соседние
цепочки продолжают работать, пока попытки не кончатся.

> **`restart: always` без предела означает, что запуск сам не завершится.** Для набора
> для разработки это ровно то, что нужно: сервер поднимается обратно, и вы работаете дальше
> до Ctrl+C. В CI это ловушка — там задавайте `restartAttempts`.

`stopped` означает, что цепочка не падала сама — её оборвали: отказом соседней цепочки либо
нажатием Ctrl+C. `timed out` — команда превысила отведённый ей предел и была снята. `skipped` —
цепочка не начиналась вовсе: то, что ей нужно по `needs`, упало или не дошло до готовности.

## Конфигурация (YAML)

Верхнеуровневый ключ — `commands`. Он сопоставляет имена цепочек наборам команд. Каждая команда —
либо обычная команда ОС, либо рецепт для Docker.

```yaml
commands: # список параллельных цепочек команд
  php-server: # имя цепочки
    artisan: # ключ команды внутри цепочки
      pipe: true                 # потоковая отдача stdout/stderr
      cmd: [ 'php', 'artisan', 'serve', '--port', '8010' ]
      dir: 'app'                 # рабочий каталог

  web-services:
    nginx-cmd:
      pipe: true
      cmd: [ 'docker', 'container', 'run', '--rm', '-p', '8090:80', '--name', 'nginx', 'nginx' ]
      format:
        cmdName: '%CMD_NAME% %CMD_ARGS%'

  docker-services: # сокращённая запись для Docker
    nginx-docker:
      docker:
        image:
          name: 'nginx'
          # tag: 'v1'            # по умолчанию 'latest'
          # pull: 'always'       # по умолчанию не указывается
        ports: [ '127.0.0.1:80:8080', '127.0.0.1:443:8443' ]
        # removeAfterAll: false  # по умолчанию true
        # cmd: 'exec'            # по умолчанию 'run'

  frontend:
    list-files:
      cmd: [ 'ls', '-la' ]         # выполняется без pipe
    yarn-dev:
      pipe: true
      cmd: [ 'yarn', 'dev' ]
      dir: 'app'

  network:
    ping-test:
      pipe: true
      cmd: [ 'ping', '-c', '3', 'ya.ru' ]
```

### Поля

- `pipe: true` — отдавать вывод потоком и запускать команду одновременно с остальными в её
  цепочке. Цепочка не завершится, пока не закончатся все её pipe-команды.
- `pipe: false` (или отсутствует) — выполнять последовательно, в порядке объявления в цепочке.
  Вывод печатается блоком после завершения команды.
- `cmd: ['bin', 'arg1', ...]` — обычная команда и её аргументы. Берётся буквально: оболочки
  нет, поэтому `&&`, пайпы и globs не раскрываются.
- `run: 'npm run dev'` — та же команда одной строкой, выполняется через оболочку (`sh -c` на
  Unix, `%COMSPEC% /c` на Windows). Нужна, когда требуются `&&`, пайп, glob или подстановка
  переменных. С `cmd` взаимоисключающа: указать оба — ошибка, а не молчаливое предпочтение
  одного из них.
- `dir: 'path'` — рабочий каталог команды. Относительные пути разрешаются от **файла
  конфигурации**, а не от текущего каталога, поэтому конфигурация, закоммиченная рядом с
  проектом, работает откуда угодно. Несуществующий путь даёт предупреждение при старте, а не
  ошибку: каталог может создаваться предыдущей командой цепочки.
- `timeout: 30s` — снять команду, если она работает дольше. Принимается любая длительность Go
  (`500ms`, `30s`, `1m30s`); голое число отвергается, потому что `timeout: 30` читается как
  секунды, но без единицы измерения ничего не значит. Команда снимается так же, как по Ctrl+C, —
  сначала сигнал, убийство только если не вышла сама, — поэтому всё, что она успела напечатать,
  будет показано. Перекрывает `-timeout`; без того и другого предела нет.
- `restart: never | on-failure | always` — перезапускать команду после завершения. `never`
  (умолчание) выполняет её один раз. `on-failure` перезапускает после любого неуспеха, включая
  снятие по собственному `timeout`. `always` перезапускает и после успешного выхода — в этом всё
  отличие одного от другого.
- `restartAttempts: 5` — сколько всего раз команда может быть запущена. `0` или отсутствие
  означает «без ограничения». Когда попытки кончаются, цепочка падает, а код возврата последнего
  отказа по-прежнему пробрасывается наружу.
- `restartDelay: 1s` — сколько ждать перед первым перезапуском; дальше задержка удваивается,
  до тридцати секунд. Именно её рост не даёт `always` на мгновенно падающей команде занять
  процессор.
- `disable: true` — отключить команду, не удаляя её из конфигурации. Отключённые команды видны в
  предпросмотре Flow и пропускаются при выполнении. По умолчанию `false`.
- `env: { KEY: value }` — переменные окружения команды. Они **добавляются** к окружению, с
  которым запущен сам `parallel`, а не заменяют его, поэтому переписывать `PATH` не нужно. При
  совпадении ключа побеждает значение из конфигурации. Для команд в режиме `docker` переменные
  передаются **контейнеру** — см. [Режим Docker](#режим-docker).
- `envFile: .env` — загрузить переменные окружения из файла или нескольких:
  `envFile: [ .env, .env.local ]`. Пути разрешаются от файла конфигурации, как и `dir`.
  Отсутствующий файл — ошибка, а не тишина: пропущенный `envFile` дал бы запуск без половины
  настроек. Тот же ключ работает и на верхнем уровне, рядом с `commands`, — там он действует
  на все команды.
- `format.cmdName` — шаблон отображаемого имени. Поддерживает подстановки:
    - `%CMD_NAME%` — имя команды (`Name` либо `Cmd`)
    - `%CMD_ARGS%` — аргументы, соединённые пробелом

```yaml
commands:
  api:
    serve:
      pipe: true
      cmd: [ 'go', 'run', './cmd/api' ]
      env:
        APP_ENV: development
        PORT: '8080'
```

### Зависимости между цепочками

Цепочка может дождаться другой через `needs`, а команда — сказать, когда она считается готовой:

```yaml
maxParallel: 4          # верхний уровень: не больше четырёх цепочек разом
commands:
  db:
    postgres:
      pipe: true
      cmd: [ 'docker', 'run', '--rm', '-p', '5432:5432', 'postgres:17' ]
      ready:
        tcp: '127.0.0.1:5432'     # либо exec: [...], либо logLine: '...'
        timeout: 30s
  api:
    needs: [ db ]
    serve:
      pipe: true
      cmd: [ 'go', 'run', './cmd/api' ]
```

`ready` принимает ровно одно условие — два сразу это ошибка, потому что неясно, какое из них
главное:

- `tcp: 'host:port'` — адрес начал принимать соединения;
- `exec: [ 'pg_isready', '-q' ]` — команда завершилась с нулевым кодом;
- `logLine: 'ready to accept'` — текст появился в выводе цепочки (stdout или stderr).

`timeout` по умолчанию 30 секунд. Когда он истекает, зависимые цепочки не запускаются, а сводка
называет условие, которого не дождались.

**Цепочка без `ready` считается готовой, когда успешно завершилась.** Миграции и сборки не
слушают портов, и «дождаться» для них означает именно это. Цепочка с условием открывает дорогу,
как только условие выполнено, — завершаться ей не нужно, и ради этого всё и затевалось: сервер
не завершается никогда.

`needs` — **зарезервированный ключ** внутри цепочки: все остальные ключи там считаются именами
команд. Назвать команду `needs` больше нельзя, и попытка падает с объяснением.

Отбор подмножества подтягивает то, от чего оно зависит: `parallel api` запустит и `db`, и это
видно в `-list`. Цикл в зависимостях отвергается до запуска, и ошибка выписывает сам цикл
(`a -> b -> c -> a`).

`maxParallel` (или флаг `-jobs n`, который его перекрывает) ограничивает число одновременно
работающих цепочек. Ожидание предшественника происходит **до** взятия слота, поэтому лимит
не может привести к взаимоблокировке.

### Переменные окружения

Четыре источника, от слабого к сильному:

| Источник | Замечание |
|---|---|
| окружение, с которым запущен сам `parallel` | наследуется, перечислять не нужно |
| верхнеуровневый `envFile` | действует на все команды |
| собственный `envFile` команды | накладывается сверху |
| `env` команды | побеждает при совпадении |

Значения могут ссылаться на другие переменные через `${VAR}` или `${VAR:-умолчание}`.
Подстановка выполняется в значениях `env`, в `dir` и в элементах `cmd`:

```yaml
envFile: .env
commands:
  api:
    serve:
      dir: '${PROJECT_ROOT}/api'
      cmd: [ 'go', 'run', '${TARGET:-./cmd/api}' ]
      env:
        URL: 'http://localhost:${PORT}'
```

Три правила, которые стоит знать:

- **Тело `run:` намеренно не трогается.** Оно уходит в оболочку, а та раскрывает `$VAR` сама;
  второе раскрытие дало бы либо двойное, либо расхождение с тем, чего ждут от шелла. Пишите
  `run: 'echo $PORT'` — разрешит оболочка.
- **Голый `$VAR` не раскрывается никогда** — только форма `${...}`. В аргументах команд доллар
  встречается сам по себе (`awk '{print $1}'`), и съедать его молча хуже, чем потребовать
  скобки. Литеральная `${` пишется как `$${`.
- **Ссылка на переменную без значения и без умолчания — ошибка** с её именем, а не пустая
  строка: пустая строка тихо ломает пути и адреса, и узнаёшь об этом по поведению команды,
  а не из сообщения.
- **Подстановки не вкладываются.** `${A:-${B:-x}}` отвергается: умолчание ограничено первой
  закрывающей скобкой, поэтому внутренняя ссылка уехала бы в аргумент текстом. Формы оболочки,
  которые этот синтаксис не распознаёт, — например `${#arr[@]}` — проходят нетронутыми.

Файл `.env` читается так: строки-комментарии, начинающиеся с `#`, и пустые пропускаются;
необязательная приставка `export ` снимается; строка делится по **первому** `=`; значение
в парных кавычках освобождается от них как есть, без обработки экранирования. У значения без
кавычек всё от ` #` считается комментарием — если решётка нужна в самом значении, возьмите
его в кавычки.

> В режиме Docker `env` превращается в `-e KEY=VALUE`, поэтому верхнеуровневый `envFile`
> доедет и до контейнеров. Обычно это и нужно, но означает, что в контейнер уходят все
> переменные файла.

### Режим Docker

Если задана секция `docker`, утилита сама собирает итоговую команду `docker`: добавляет `--rm`
(если не указано `removeAfterAll: false`), применяет политику `pull` и пробрасывает порты. Такие
команды всегда выполняются с `pipe: true` ради живых логов, поэтому запускаются одновременно, а
цепочка дожидается их завершения.

`env` превращается в аргументы `-e KEY=VALUE`, поэтому переменные доходят до **контейнера**, а не
до процесса клиента `docker`. Кроме образа режим понимает `ports`, `volumes`, `network` и `args`:

```yaml
commands:
  services:
    db:
      docker:
        image: { name: postgres, tag: '17' }
        ports: [ '5432:5432' ]
        volumes: [ './data:/var/lib/postgresql/data' ]
        network: app-net
        args: [ '-c', 'max_connections=200' ]   # команда самого контейнера
      env:
        POSTGRES_PASSWORD: secret
```

соберёт `docker run --name db --rm -p 5432:5432 -v <каталог-конфигурации>/data:/var/lib/postgresql/data --network app-net -e POSTGRES_PASSWORD=secret postgres:17 -c max_connections=200`.

> **`cmd` — это подкоманда самого `docker`, а не команда контейнера.** `cmd: 'exec'` выбирает
> `docker exec` и читается ровно наоборот тому, чего можно ожидать. То, что должно выполняться
> **внутри** контейнера, задаётся полем `args`. Исправить имя нельзя: `docker.*` входит
> в замороженный контракт `v1`.

Флаги всегда идут до имени образа, а `args` — строго после: всё, что после образа, `docker`
считает командой контейнера. У тома хостовый путь, начинающийся с `./` или `../`, разрешается
от файла конфигурации, как и `dir`; всё прочее не трогается, поэтому `data:/var/lib` остаётся
именованным томом, а не превращается в каталог.

Пример отключения команд (работает и для обычной формы, и для docker):

```yaml
commands:
  api:
    serve:
      pipe: true
      disable: true           # попадёт в список, но не выполнится
      cmd: [ 'go', 'run', './cmd/api' ]

  docker-services:
    nginx:
      disable: true           # будет пропущена
      docker:
        image:
          name: nginx
```

## Как это выполняется

- Каждая цепочка стартует одновременно с остальными.
- Внутри цепочки:
    - Команды с `pipe: false` выполняются последовательно, ровно в том порядке, в каком записаны
      в YAML (порядок цепочек и команд детерминирован и не меняется от запуска к запуску).
    - Команды с `pipe: true` стартуют сразу и работают параллельно с остальными в той же цепочке;
      цепочка завершится только после того, как закончится каждая из них.
    - Если падает не-pipe команда, следующие команды этой цепочки не запускаются, а уже
      работающие pipe-команды дожидаются.
- При `pipe: true` stdout и stderr отдаются потоком и раскрашиваются по цепочке.
- У команд без pipe вывод показывается оформленным блоком после завершения.

Пример смешивания pipe и не-pipe команд в одной цепочке:

```yaml
commands:
  api:
    migrate:
      cmd: [ 'go', 'run', './cmd/migrate' ] # идёт последовательно, пока long-runner пишет в поток

    long-runner:
      pipe: true
      cmd: [ 'go', 'run', './cmd/api' ]

    health-check:
      pipe: true                          # стартует сразу; цепочка дождётся её в конце
      cmd: [ 'curl', '-s', 'http://localhost:8080/health' ]
```

## Мягкое завершение

Утилита перехватывает `SIGINT`, `SIGTERM`, `SIGQUIT` и пересылает тот же самый сигнал всей группе
процессов каждой работающей команды (`setpgid` + сигнал группе). Затем ждёт завершения в пределах
небольшого таймаута и только после этого добивает оставшиеся группы принудительно.

> Про платформы: на Windows произвольные POSIX-сигналы доставить нельзя. Дочерние процессы
> запускаются в новой группе (`CREATE_NEW_PROCESS_GROUP`) и получают консольное событие
> `CTRL_BREAK`, которое умеют обрабатывать рантаймы Node.js, Python, .NET и Go. Если процесс
> после этого не вышел, он убивается — та же двухступенчатая лестница, что и на Unix.

Что это означает на практике:

- Нажмите Ctrl+C **один раз**, чтобы штатно остановить всё. Долгоживущие потомки, умеющие
  обрабатывать сигналы (`node`, `php artisan serve`, `yarn`), успеют прибраться перед выходом.
- Нажмите Ctrl+C **дважды**, чтобы прекратить ожидание и убить все процессы немедленно.
- Третий Ctrl+C завершает сам `parallel` сразу же, со статусом `130`.

Вывод при завершении не обрезается: всё, что команда успела напечатать до выхода, будет прочитано
и показано, включая последние строки перед смертью процесса.

## Предпросмотр Flow

Перед выполнением утилита печатает разбор вашего Flow — цепочки и команды, — чтобы было видно,
что именно запустится. Пример:

```
Flow structure:
  Chain 1: server
    [1] php
        Exec : php artisan queue:work --queue=image-resizing
        Dir  : /path/to/app
        Pipe : true
        Name : %CMD_NAME%
```

## Примеры

Запуск с конфигурацией по умолчанию из текущего каталога:

```shell
parallel
```

Запуск с явным путём к конфигурации:

```shell
parallel -f examples/full.yaml
```

Минимальная конфигурация для двух параллельных команд:

```yaml
commands:
  api:
    serve:
      pipe: true
      cmd: [ 'go', 'run', './cmd/api' ]
  ui:
    dev:
      pipe: true
      cmd: [ 'yarn', 'dev' ]
      dir: 'web'
```

## Решение проблем

- Команда сразу завершается без вывода
    - Проверьте `cmd` и аргументы, убедитесь, что бинарник есть в `PATH`
    - Проверьте, что `dir` указывает на существующий каталог
- В `cmd` записана целая строка с пайпом или `&&` — команда не находится
    - Значение `cmd` — это программа и её аргументы, а не строка для оболочки. Оболочку надо
      звать явно: `cmd: [ 'sh', '-c', 'a && b' ]`
- Конфигурация не найдена
    - В сообщении перечислены имена, которые искались. Учтите: путь из `-f` берётся буквально и
      наверху не ищется — опечатка в `-f` обязана падать, а не подхватывать чужую конфигурацию
      из родительского каталога
- Docker-команда продолжает работать после Ctrl+C
    - Сигнал отправляется группе процессов; убедитесь, что процесс в контейнере обрабатывает
      `SIGTERM` и завершается без задержки
- Ошибка YAML: «invalid flow configuration»
    - Утилита проверяет, что в каждой цепочке есть хотя бы одна команда, а у каждой команды
      непустой `cmd`

## Совместимость

Начиная с `v1.0.0` замораживается следующее — оно не изменится без выпуска `v2`:

- **Флаги CLI** — `-f <path>`, `-v`, `--version`, `-list`, `-dry-run`, `-except`, `-no-color`,
  `-keep-going`, `-timeout`, `-jobs`;
  позиционные аргументы отбирают цепочки, `--` включает режим без конфигурации; имя
  конфигурации по умолчанию
  `.parallelrc.yaml` (принимается и `.parallelrc.yml`), поиск — в текущем каталоге и выше.
- **Коды возврата** — `0` при успехе; `1` при ошибке запуска или конфигурации; `124` при
  таймауте; собственный статус упавшей команды пробрасывается наружу.
- **Схема конфигурации** — верхнеуровневые ключи `commands`, `failFast`, `envFile`
  и `maxParallel`; ключ цепочки `needs`; поля команды `cmd`, `run`, `timeout`, `ready`,
  `restart`, `restartAttempts`, `restartDelay`, `envFile`, `dir`, `pipe`,
  `disable`, `env`, `format.cmdName`, `docker.*`, а также подстановки `%CMD_NAME%` и `%CMD_ARGS%`.
- **Семантика выполнения** — цепочки идут параллельно; внутри цепочки не-`pipe` команды идут
  последовательно в порядке YAML, `pipe`-команды — одновременно, и цепочка дожидается всех.

Осознанно **не** замораживается и может измениться в любом релизе: точный формат и порядок строк
лога, палитра, внешний вид предпросмотра Flow и формулировки сообщений об ошибках.

Путь модуля остаётся `github.com/efureev/parallel` — суффикс `/vN` требуется только начиная с
`v2`. Импортируемого Go API нет: всё лежит под `internal/`, то есть `parallel` — это команда, а не
библиотека.

## Разработка

Запуск тестов:

```shell
go test ./...
```

Сборка бинарника:

```shell
go build -o parallel ./cmd/parallel
```

В репозитории есть цели `make` — они работают внутри Docker, локальные инструменты не нужны:

- `make test` — линтеры и тесты
- `make lint` — `golangci-lint`
- `make fmt` — форматирование (goimports + `gofmt -s` + `go mod tidy`)

Список заметных изменений — в [`CHANGELOG.md`](CHANGELOG.md). Перед pull request стоит
прочитать [`CONTRIBUTING.md`](CONTRIBUTING.md): у линтера, границ слоёв и сборки под Windows
есть требования, не очевидные из кода.

Проект следует стандартной раскладке Go, по пакету на слой:

```
cmd/parallel/        точка входа: сборка зависимостей и код возврата
internal/
  buildinfo/         метаданные версии, подставляются через -ldflags
  flow/              домен: Flow, CommandChain, Command, валидация
  config/            схема YAML, загрузка, сборка доменного Flow
  runner/            супервизия процессов, реестр, группы процессов
  ui/                порт логгера, рендер вывода, палитра, предпросмотр Flow
  cli/               флаги, сигналы, связывание зависимостей
```

Зависимости направлены строго в одну сторону: `cli → {config, flow, runner, ui}`,
`runner → {flow, ui}`, `config → flow`, `ui → flow`, а `flow` не зависит ни от чего.
Правило проверяется `depguard` в `golangci-lint`, а не держится на договорённости.
