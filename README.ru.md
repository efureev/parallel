*Read this in [English](README.md).*

Небольшая CLI-утилита для параллельного запуска нескольких консольных команд с читаемым цветным
выводом. Полезна при локальной разработке, когда нужно поднять сразу несколько сервисов и
инструментов: веб-сервер, очереди, сборщики, вотчеры.

Коротко о главном:

- Параллельное выполнение независимых цепочек
- Внутри цепочки: обычные команды идут последовательно, команды с `pipe: true` — одновременно
- Читаемые цветные логи с раскраской по цепочкам и потоковой отдачей (`pipe`)
- Мягкое завершение: исходный сигнал ОС уходит всей группе процессов, утилита дожидается их
- Конфигурация в YAML, helpers для Docker, шаблоны имён

В этом файле собраны типичные сценарии и практические примеры.

## Установка

Требования: Go 1.26+ (проверено на macOS, Linux, Windows)

```shell
go install github.com/efureev/parallel@latest
```

Бинарник окажется в `$(go env GOPATH)/bin/parallel`.

## Быстрый старт

Если в рабочем каталоге лежит файл `.parallelrc.yaml`:

```shell
parallel
```

Если конфигурация лежит в другом месте:

```shell
parallel -f /path/to/config/flow.yaml
```

В репозитории есть два готовых примера, их не нужно править перед запуском:

```shell
parallel -f examples/basic.yaml   # две цепочки: последовательная и потоковая
parallel -f examples/full.yaml    # env, dir, disable и режим Docker
```

Поддерживаемые флаги:

- `-f` — путь к YAML-конфигурации (по умолчанию `.parallelrc.yaml`)
- `-log-level` — `debug`, `info` (по умолчанию), `warn` или `error`
- `-v`, `--version` — информация о версии
- `-h`, `--help` — справка

Неизвестные поля в конфигурации отвергаются с указанием точной позиции и подсказкой: опечатка
вроде `pipeline:` вместо `pipe:` падает громко, а не меняет поведение молча.

### Коды возврата

Утилита пригодна для скриптов и CI и возвращает осмысленный код:

- `0` — все цепочки отработали успешно (а также для `-v` и `-h`).
- `1` — ошибка запуска или конфигурации: файл не найден, неизвестное поле, неверный флаг.
- *собственный код команды* — если команда упала, её статус пробрасывается наружу, поэтому
  `parallel -f flow.yaml || echo $?` показывает, что произошло на самом деле. Если упало
  несколько команд, побеждает первая в порядке объявления в конфигурации.

Это позволяет безопасно использовать `parallel` в скриптах и пайплайнах
(например, `parallel -f flow.yaml && next-step`).

## Конфигурация (YAML)

Верхнеуровневый ключ — `commands`. Он сопоставляет имена цепочек наборам команд. Каждая команда —
либо обычная команда ОС, либо рецепт для Docker.

```yaml
commands: # список параллельных цепочек команд
  php-server: # имя цепочки
    artisan: # ключ команды внутри цепочки
      pipe: true                 # потоковая отдача stdout/stderr
      cmd: [ 'php', 'artisan', 'serve', '--port', '8010' ]
      dir: 'app'                 # рабочий каталог

  web-services:
    nginx-cmd:
      pipe: true
      cmd: [ 'docker', 'container', 'run', '--rm', '-p', '8090:80', '--name', 'nginx', 'nginx' ]
      format:
        cmdName: '%CMD_NAME% %CMD_ARGS%'

  docker-services: # сокращённая запись для Docker
    nginx-docker:
      docker:
        image:
          name: 'nginx'
          # tag: 'v1'            # по умолчанию 'latest'
          # pull: 'always'       # по умолчанию не указывается
        ports: [ '127.0.0.1:80:8080', '127.0.0.1:443:8443' ]
        # removeAfterAll: false  # по умолчанию true
        # cmd: 'exec'            # по умолчанию 'run'

  frontend:
    list-files:
      cmd: [ 'ls', '-la' ]         # выполняется без pipe
    yarn-dev:
      pipe: true
      cmd: [ 'yarn', 'dev' ]
      dir: 'app'

  network:
    ping-test:
      pipe: true
      cmd: [ 'ping', '-c', '3', 'ya.ru' ]
```

### Поля

- `pipe: true` — отдавать вывод потоком и запускать команду одновременно с остальными в её
  цепочке. Цепочка не завершится, пока не закончатся все её pipe-команды.
- `pipe: false` (или отсутствует) — выполнять последовательно, в порядке объявления в цепочке.
  Вывод печатается блоком после завершения команды.
- `cmd: ['bin', 'arg1', ...]` — обычная команда и её аргументы.
- `dir: 'path'` — рабочий каталог команды. Относительные пути разрешаются от **файла
  конфигурации**, а не от текущего каталога, поэтому конфигурация, закоммиченная рядом с
  проектом, работает откуда угодно. Несуществующий путь даёт предупреждение при старте, а не
  ошибку: каталог может создаваться предыдущей командой цепочки.
- `disable: true` — отключить команду, не удаляя её из конфигурации. Отключённые команды видны в
  предпросмотре Flow и пропускаются при выполнении. По умолчанию `false`.
- `env: { KEY: value }` — переменные окружения команды. Они **добавляются** к окружению, с
  которым запущен сам `parallel`, а не заменяют его, поэтому переписывать `PATH` не нужно. При
  совпадении ключа побеждает значение из конфигурации. Для команд в режиме `docker` переменные
  передаются **контейнеру** — см. [Режим Docker](#режим-docker).
- `format.cmdName` — шаблон отображаемого имени. Поддерживает подстановки:
    - `%CMD_NAME%` — имя команды (`Name` либо `Cmd`)
    - `%CMD_ARGS%` — аргументы, соединённые пробелом

```yaml
commands:
  api:
    serve:
      pipe: true
      cmd: [ 'go', 'run', './cmd/api' ]
      env:
        APP_ENV: development
        PORT: '8080'
```

### Режим Docker

Если задана секция `docker`, утилита сама собирает итоговую команду `docker`: добавляет `--rm`
(если не указано `removeAfterAll: false`), применяет политику `pull` и пробрасывает порты. Такие
команды всегда выполняются с `pipe: true` ради живых логов, поэтому запускаются одновременно, а
цепочка дожидается их завершения.

`env` превращается в аргументы `-e KEY=VALUE`, поэтому переменные доходят до **контейнера**, а не
до процесса клиента `docker`:

```yaml
commands:
  services:
    cache:
      docker:
        image:
          name: redis
        ports: [ '6379:6379' ]
      env:
        REDIS_ARGS: '--save 60 1'
```

соберёт `docker run --name cache --rm -p 6379:6379 -e REDIS_ARGS=--save 60 1 redis:latest`.
Ключи сортируются, а флаги всегда стоят до имени образа: всё, что идёт после образа, `docker`
принимает за команду контейнера. Переменную для самого клиента `docker` (`DOCKER_HOST` и
подобные) задавайте в оболочке, из которой запускается `parallel`.

Пример отключения команд (работает и для обычной формы, и для docker):

```yaml
commands:
  api:
    serve:
      pipe: true
      disable: true           # попадёт в список, но не выполнится
      cmd: [ 'go', 'run', './cmd/api' ]

  docker-services:
    nginx:
      disable: true           # будет пропущена
      docker:
        image:
          name: nginx
```

## Как это выполняется

- Каждая цепочка стартует одновременно с остальными.
- Внутри цепочки:
    - Команды с `pipe: false` выполняются последовательно, ровно в том порядке, в каком записаны
      в YAML (порядок цепочек и команд детерминирован и не меняется от запуска к запуску).
    - Команды с `pipe: true` стартуют сразу и работают параллельно с остальными в той же цепочке;
      цепочка завершится только после того, как закончится каждая из них.
    - Если падает не-pipe команда, следующие команды этой цепочки не запускаются, а уже
      работающие pipe-команды дожидаются.
- При `pipe: true` stdout и stderr отдаются потоком и раскрашиваются по цепочке.
- У команд без pipe вывод показывается оформленным блоком после завершения.

Пример смешивания pipe и не-pipe команд в одной цепочке:

```yaml
commands:
  api:
    migrate:
      cmd: [ 'go', 'run', './cmd/migrate' ] # идёт последовательно, пока long-runner пишет в поток

    long-runner:
      pipe: true
      cmd: [ 'go', 'run', './cmd/api' ]

    health-check:
      pipe: true                          # стартует сразу; цепочка дождётся её в конце
      cmd: [ 'curl', '-s', 'http://localhost:8080/health' ]
```

## Мягкое завершение

Утилита перехватывает `SIGINT`, `SIGTERM`, `SIGQUIT` и пересылает тот же самый сигнал всей группе
процессов каждой работающей команды (`setpgid` + сигнал группе). Затем ждёт завершения в пределах
небольшого таймаута и только после этого добивает оставшиеся группы принудительно.

> Про платформы: на Windows произвольные POSIX-сигналы доставить нельзя. Дочерние процессы
> запускаются в новой группе (`CREATE_NEW_PROCESS_GROUP`) и получают консольное событие
> `CTRL_BREAK`, которое умеют обрабатывать рантаймы Node.js, Python, .NET и Go. Если процесс
> после этого не вышел, он убивается — та же двухступенчатая лестница, что и на Unix.

Что это означает на практике:

- Нажмите Ctrl+C **один раз**, чтобы штатно остановить всё. Долгоживущие потомки, умеющие
  обрабатывать сигналы (`node`, `php artisan serve`, `yarn`), успеют прибраться перед выходом.
- Нажмите Ctrl+C **дважды**, чтобы прекратить ожидание и убить все процессы немедленно.
- Третий Ctrl+C завершает сам `parallel` сразу же, со статусом `130`.

Вывод при завершении не обрезается: всё, что команда успела напечатать до выхода, будет прочитано
и показано, включая последние строки перед смертью процесса.

## Предпросмотр Flow

Перед выполнением утилита печатает разбор вашего Flow — цепочки и команды, — чтобы было видно,
что именно запустится. Пример:

```
Flow structure:
  Chain 1: server
    [1] php
        Exec : php artisan queue:work --queue=image-resizing
        Dir  : /path/to/app
        Pipe : true
        Name : %CMD_NAME%
```

## Примеры

Запуск с конфигурацией по умолчанию из текущего каталога:

```shell
parallel
```

Запуск с явным путём к конфигурации:

```shell
parallel -f examples/full.yaml
```

Минимальная конфигурация для двух параллельных команд:

```yaml
commands:
  api:
    serve:
      pipe: true
      cmd: [ 'go', 'run', './cmd/api' ]
  ui:
    dev:
      pipe: true
      cmd: [ 'yarn', 'dev' ]
      dir: 'web'
```

## Решение проблем

- Команда сразу завершается без вывода
    - Проверьте `cmd` и аргументы, убедитесь, что бинарник есть в `PATH`
    - Проверьте, что `dir` указывает на существующий каталог
- В `cmd` записана целая строка с пайпом или `&&` — команда не находится
    - Значение `cmd` — это программа и её аргументы, а не строка для оболочки. Оболочку надо
      звать явно: `cmd: [ 'sh', '-c', 'a && b' ]`
- Конфигурация не найдена при запуске из подкаталога
    - Поиск идёт только в текущем каталоге и только по имени `.parallelrc.yaml` (расширение
      `.yml` не подходит). Укажите путь явно через `-f`
- Docker-команда продолжает работать после Ctrl+C
    - Сигнал отправляется группе процессов; убедитесь, что процесс в контейнере обрабатывает
      `SIGTERM` и завершается без задержки
- Ошибка YAML: «invalid flow configuration»
    - Утилита проверяет, что в каждой цепочке есть хотя бы одна команда, а у каждой команды
      непустой `cmd`

## Совместимость

Начиная с `v1.0.0` замораживается следующее — оно не изменится без выпуска `v2`:

- **Флаги CLI** — `-f <path>`, `-v`, `--version`; путь к конфигурации по умолчанию
  `.parallelrc.yaml`.
- **Коды возврата** — `0` при успехе; `1` при ошибке запуска или конфигурации; собственный
  статус упавшей команды пробрасывается наружу.
- **Схема конфигурации** — верхнеуровневый ключ `commands` и поля команды `cmd`, `dir`, `pipe`,
  `disable`, `env`, `format.cmdName`, `docker.*`, а также подстановки `%CMD_NAME%` и `%CMD_ARGS%`.
- **Семантика выполнения** — цепочки идут параллельно; внутри цепочки не-`pipe` команды идут
  последовательно в порядке YAML, `pipe`-команды — одновременно, и цепочка дожидается всех.

Осознанно **не** замораживается и может измениться в любом релизе: точный формат и порядок строк
лога, палитра, внешний вид предпросмотра Flow и формулировки сообщений об ошибках.

Путь модуля остаётся `github.com/efureev/parallel` — суффикс `/vN` требуется только начиная с
`v2`. Импортируемого Go API нет: всё лежит под `internal/`, то есть `parallel` — это команда, а не
библиотека.

## Разработка

Запуск тестов:

```shell
go test ./...
```

Сборка бинарника:

```shell
go build -o parallel ./cmd/parallel
```

В репозитории есть цели `make` — они работают внутри Docker, локальные инструменты не нужны:

- `make test` — линтеры и тесты
- `make lint` — `golangci-lint`
- `make fmt` — форматирование (goimports + `gofmt -s` + `go mod tidy`)

Список заметных изменений — в [`CHANGELOG.md`](CHANGELOG.md).

Проект следует стандартной раскладке Go, по пакету на слой:

```
cmd/parallel/        точка входа: сборка зависимостей и код возврата
internal/
  buildinfo/         метаданные версии, подставляются через -ldflags
  flow/              домен: Flow, CommandChain, Command, валидация
  config/            схема YAML, загрузка, сборка доменного Flow
  runner/            супервизия процессов, реестр, группы процессов
  ui/                порт логгера, рендер вывода, палитра, предпросмотр Flow
  cli/               флаги, сигналы, связывание зависимостей
```

Зависимости направлены строго в одну сторону: `cli → {config, flow, runner, ui}`,
`runner → {flow, ui}`, `config → flow`, `ui → flow`, а `flow` не зависит ни от чего.
Правило проверяется `depguard` в `golangci-lint`, а не держится на договорённости.
